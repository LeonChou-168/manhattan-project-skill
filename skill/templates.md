# 文书模板

八段工作流每一步的产出物，外加交付后的复盘。所有文书一页以内；超过一页说明想复杂了。

**执行协议**：产物落在项目根目录 `.manhattan/`，开段先读上一段产物，**未落盘即视为未完成**。
追加写、不覆盖历史，跨会话可恢复。

| 文件 | 产出阶段 | 用途 |
|---|---|---|
| `.manhattan/objective.md` | 第 1 段 | 作战目标 |
| `.manhattan/charter.md` | 第 2 段 | 授权书 |
| `.manhattan/lines/<线名>.md` | 第 4 段 | 线卡（一线一文件） |
| `.manhattan/briefing.md` | 第 4 段 | 底课文档 |
| `.manhattan/tree.md` | 第 4 段 | 问题分解树 |
| `.manhattan/reports/<线名>-<日期>.md` | 第 5 段 | 判别点报告（裁决会唯一输入） |
| `.manhattan/decisions.md` | 第 6 段 | 裁决记录（追加写） |
| `.manhattan/assumptions.md` | 全程 | 假设登记（失效自动重审） |
| `.manhattan/gate-test.md` | 第 7 段 | 试验门检查单 |
| `.manhattan/gate-release.md` | 第 8 段 | 发布门检查单 |
| `.manhattan/retro.md` | 交付后 | 复盘 |

## 1. 作战目标（objective.md）

```markdown
# 作战目标：<项目名>
- 交付物：<可验收的东西，一句话>
- 截止：<日期或外部触发事件>
- 验收测量：<用什么测、谁测、测量工具是否独立于制造过程>
- 当前最大不确定性：<哪个参数/路线，差几个数量级>
- 不做清单：<明确排除的范围>
- 用户确认：<日期 / 原话摘要>
```

**完成判据**：交付物能被第三方一句话验收；截止外部给定；验收测量与制造物理独立；有不做清单；用户明确点头。
**进入下一段前提**：用户确认这一版目标。
**常见翻车**：把 KPI 当目标；验收标准由制造方自己定义；截止写「尽快」。

## 2. 授权书（charter.md）

```markdown
# 授权书
- 用户独裁事项：路线取舍、杀线签字、发布签字、<按项目补充>
- AI 先斩后奏事项：执行细节、环境配置、探针实验（单次预算上限 <X>）、<补充>
- 必须会签事项：改作战目标、改死刑条件、扩编制
- 用户第一交付物：用自己话重述项目真正的瓶颈（一段话，与作战目标对照）
- 生效时间 / 双方确认：
```

**完成判据**：三类事项逐条写明且无重叠；先斩后奏有预算上限；用户已产出「重述瓶颈」且与目标一致。
**进入下一段前提**：用户复述的瓶颈与作战目标一致；不一致则回第 1 段。
**常见翻车**：把授权写成口号（「用户领导」）；先斩后奏没有上限；用户没重述就往下走。

## 3. 底课文档（briefing.md，第 4 段产出）

```markdown
# 底课：<项目名>
- 背景与目标（3 句话内）
- 术语表：<本项目特有名词，一句话解释>
- 已冻结的接口 / 数据格式 / 测试基线
- 已知约束：时间、预算、合规、平台限制
- 禁传清单：<不进入底课的敏感信息、未验证猜想、进度评价>
- 版本：v<N>，更新时间：<日期>
```

**完成判据**：所有执行线（含子 agent 的系统上下文）使用同一版本；更新时全员同步。
**常见翻车**：每条线各写各的底课；把未验证猜想写进底课当事实。

## 4. 问题分解树（tree.md，第 4 段产出）

```markdown
# 问题分解树：<项目名>
- 交付物 ← 负责人：<谁>
  - 子问题 1 ← 负责人：<谁>（短板：<...>，协调人：<谁>）
  - 子问题 2 ← 负责人：<谁>
    - 孙问题 2.1 ← 负责人：<子 agent / 工具 / 外部服务>
```

**完成判据**：每个节点有且只有一个负责人；负责人短板有协调人补，不靠堆人；叶子节点能直接落到线卡或任务。
**常见翻车**：一个节点挂两个负责人（等于没有）；分解树只到「模块」不到「可执行任务」。

## 5. 线卡（lines/<线名>.md，第 4 段产出）

```markdown
# 线卡：<方案名>
- 负责人：<单一负责人；短板由协调人 <谁> 补足>
- 下一个判别点：<什么实验/基准，产出什么数据>
- 到达时间：<日期>；到达前预算：<时间 / 成本上限>
- 死刑条件：出现 <什么可复现数据> 即杀线，签字人：用户
- 可回收产出：<即使被杀，哪些部件 / 知识可移交>
- 降级顺位：<资源砍半时本线排第几个被杀>
- 依赖：<需要哪些线/产物先就绪，或「无」>
```

**完成判据**：判别点能产出一个可比较的标量/表格；死刑条件是数据判据而非「效果不好」；降级顺位覆盖所有线且不重复。
**常见翻车**：判别点写成「完成开发」；死刑条件没有签字人；三条线算不出唯一降级顺位。

## 6. 范围重估记录（第一个里程碑前，追加到 decisions.md）

```markdown
## 范围重估：<日期>
- 首次估计 vs 当前信息：<哪些参数被证伪 / 扩大 / 缩小>
- 结论：维持 | 扩编（加哪些线 / 人） | 缩编（先杀谁）
- 签字人：
```

**完成判据**：每个「当初想小了 / 想大了」的结论都被记录；扩编写明资源来源。
**常见翻车**：把范围重估开成进度汇报；扩编只在聊天里说，不落盘。

## 7. 接口协议（第 5 段，跨线信息交换）

```markdown
# 接口协议：<线A> ↔ <线B>
1. 交换目的：仅限对双方工作都有利的信息
2. 禁传清单：<各自的中间结论、未验证猜想、进度评价>
3. 指定通道：通过 <artifact 路径 / schema> 传递；联系人：<谁>
4. 修订机制：任一方申请、Groves 身份批准后修订
5. 高带宽例外：需 Groves 特批，事后回归本协议
```

**完成判据**：每条需要交换的线对都有协议；禁传清单明确；交换有固定格式。
**常见翻车**：跨线直接抄结论；「高带宽例外」变成常态。

## 8. 判别点报告（reports/<线名>-<日期>.md，第 5 段产出 → 第 6 段唯一输入）

```markdown
# 判别点报告：<线名> @ <日期>
- 假设：<A1、A2；来自 assumptions.md>
- 测量方法：<命令 / 脚本 / 数据集；是否独立于制造过程>
- 数值：<指标1 = <值>（置信 高/中/低）；指标2 = <值>>
- 是否触发死刑条件：<是 / 否；触发项：<条件>>
- 建议：<继续 / 杀线 / 串联 / 探索降配>
- 未决问题：<...>
```

**完成判据**：报告能独立回答「这条线的命运」，不需要执行细节；数值可复现；引用假设登记。
**常见翻车**：报告写成进度汇报；数值没有测量方法；建议越权替用户做裁决。

## 9. 裁决记录（decisions.md，每次裁决追加一条）

```markdown
### <日期> 裁决：<杀线 | 补线 | 串联 | 探索降配> — <线名>
- 触发数据：<判别点报告路径>
- 相关假设：<A1、A3>
- 结论与动作：<遣散 / 扩编 / 改流水线 / 收缩>
- 用户签字：<原话 / 时间>
- 资源去向：<人力、预算、产出移交到哪>
- 淘汰语境：在 <目标>、<假设> 下淘汰；<假设> 失效时自动重审
```

**完成判据**：每条裁决都有可复现触发数据、用户签字、淘汰语境；与假设登记双向可查。
**常见翻车**：裁决会变成技术细节评审；杀线不写淘汰语境，下一版重蹈覆辙。

## 10. 假设登记（assumptions.md，全程维护）

```markdown
| id | 假设 | 依据 | 失效条件 | 受影响线 / 裁决 | 状态 |
|---|---|---|---|---|---|
| A1 | <一句话假设> | <证据卡 / 数据> | <可观测条件> | <线名 / 裁决日期> | 有效 / 失效 / 已重审 |
```

**完成判据**：所有裁决记录引用的假设都能查到；假设失效后 24 小时内触发重审并记录。
**常见翻车**：假设只写在裁决记录里、没有统一登记；失效了不重审。

## 11. 试验门检查单（gate-test.md，第 7 段）

```markdown
# 试验门：<项目名>
- [ ] 验收测量独立于制造过程（独立性证据：<独立测试集 / 外部评审 / 用户实测>）
- [ ] 与作战目标一致（逐条对应指标）
- [ ] 矛盾读数已闭环（处置：<复测 / 归因 / 修复>）
- [ ] 规格外偏差已处置（改规格并附论证 / 消除偏差；没有第三状态）
- [ ] 已知问题计数：<n>（同一问题被标「已知」≥3 次 → 升级为阻塞项）
- 结论：通过 / 不通过（不通过时的下一轮条件）
```

**完成判据**：独立性有证据而不只是声明；矛盾读数闭环；无「接受着先飞」。
**常见翻车**：用同一套工具自测自验；把「没复现」当「没问题」；把已知问题计数当摆设。

## 12. 发布门检查单（gate-release.md，第 8 段）

```markdown
# 发布门：<项目名>
- 试验门状态：通过（<日期 / gate-test.md 路径>）
- 评审席位：<承担后果方：用户本人 / 运维 / 客服 / 受影响系统代表>
- 影响面：<用户 / 数据 / 依赖 / 合规>
- 回滚方案：<步骤 + 演练结果>
- 时机：<窗口 / 灰度比例 / 观察期>
- 技术负责人意见：<...>（无一票通过权）
- 结论：发布 / 推迟（原因与复评日期）
```

**完成判据**：试验门全绿只是入场券；席位里有承担后果方；回滚有演练；技术评审与发布评审不是同一批人。
**常见翻车**：把「技术通过」等同「可以上线」；发布评审走过场。

## 13. 复盘（retro.md，交付后 10 分钟）

```markdown
# 复盘：<项目名>
1. 哪条线本可以更早被杀 / 更早补？判据是否失效？
2. 哪个验收 / 判别测量其实不独立？
3. 哪些假设变了但没触发重审？
4. 可沉淀的算子 / 反例 → 补进 corpus/cards/ <card-id>？
```

**完成判据**：每条结论有具体证据指向；沉淀项有明确去处（补卡 / 改模板 / 不沉淀）。
**常见翻车**：复盘写成庆功会；结论只有「下次注意」。

## /grill 问题库（按阶段分配，一次只问一题）

| 阶段 | 问题 | 为什么在这个阶段问 |
|---|---|---|
| 2 授权 | **Q9** 用你自己的话说：真正的瓶颈在哪？ | 授权后的第一交付物，验证目标是否被真正理解 |
| 3 /grill | **Q1** 交付物是什么、谁验收、测量与制造是否独立？ | 决定验收口径 |
| 3 /grill | **Q2** 关键参数能估到 ±50% 内吗？不能——开几条线？ | 决定单线退出还是并行 |
| 3 /grill | **Q7** 需求里哪些是物理/用户约束，哪些是立项话术？ | 剥离伪需求 |
| 4 招募 | **Q3** 每条线的下一个判别点、到达时间、到达前预算？ | 写线卡 |
| 4 招募 | **Q4** 这条线出现什么数据就地处决？谁签字？ | 写死刑条件 |
| 4 招募 | **Q5** 资源砍半先杀谁？ | 写降级顺位 |
| 4 招募 | **Q11** 有没有一条「本期用不上但下一局重要」的探索线？封多少预算？ | 决定探索线 |
| 5 并行 | **Q10** 哪些琐事在消耗你的注意力？列出来，我接走。 | 行政卸载 |
| 6 裁决 | **Q6** 两条线的中间产物能不能互相喂？交接格式？ | 判断串联可能 |
| 8 发布 | **Q8** 试验全绿之后，谁坐在发布评审桌上？ | 提前锁定发布门席位 |

**准入 3 问**（开工时问，非 11 问之一）：

1. 是否存在 ≥2 个互相竞争的方案，且单一方案没有明显优势？
2. 关键参数的不确定度是否跨数量级（不是 ±50%）？
3. 失败了代价是否远大于并行探索成本？是否有真实截止？

任一答「否」→ 不启用本模式，直接常规规划。
